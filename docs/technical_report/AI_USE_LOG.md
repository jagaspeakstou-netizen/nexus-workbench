# AI-Use Log

PASS Science Works R&D Internship 2026–2027 — NEXUS Engineering
Intelligence Workbench. This log records how AI assistance (Claude,
via Claude Code) was used across this project, honestly and without
editing out mistakes. Everything below is drawn directly from the
project's actual commit history and the real tool-use record of the
development sessions — not reconstructed from memory after the fact.

## How AI was used

Claude was used as a pair-programmer across the full stack: C++ backend
implementation (all 6 engineering modules + the HTTP API layer), the
React/TypeScript frontend, GoogleTest test suites, CI/CD (GitHub Actions
Windows build pipeline), the native Windows WebView2 launcher, and this
documentation itself. The candidate directed scope and sequencing
(module order, when to move from one day's work to the next, when to
push and trigger CI), reviewed generated code and the evidence it
produced, and made the calls on tradeoffs (e.g. accepting the Performance
Lab's benchmark-design limitation as a disclosed caveat rather than
chasing a "clean" number).

Every numeric result claimed anywhere in this project (test counts,
CSV data, CI run outcomes, convergence rates) was generated by actually
running the code — not written by the AI from expectation. Where a build
or test failed, the actual failure log is what's quoted in the
architecture docs, not a paraphrase.

## AI mistakes made during generation, and how they were caught

These are instances where Claude's own first-draft output was wrong and
had to be corrected before it reached a commit. They are listed here
because this project's standing rule was to disclose debugging history
rather than silently clean it up.

1. **`windows/launcher/Launcher.cpp`, first draft (Day 8–9, Windows
   packaging).** The first generated version included a nonsensical
   `#include <wil/com.h>` (a header never actually used) and a stray,
   incoherent comment that didn't belong in working code. **Caught by
   Claude itself**, mid-session, before the file was shown as finished —
   rewritten cleanly using the standard `Microsoft::WRL::Callback`
   WebView2 async pattern. The user did not review or approve the broken
   draft; it was never presented as final.

2. **`backend/src/neural/neural.cpp`'s `backward()`, first draft (Day
   9, Neural Computation).** The first generated implementation of the
   backprop gradient function was confused placeholder logic — a
   `copysign(sqrt(...))` expression that computed nothing meaningful,
   or correct chain-rule math. **Caught by Claude itself** before
   presenting it: explicitly flagged mid-session ("I need to redo that
   — I drifted into writing confused placeholder logic instead of the
   actual implementation"), then rewritten with the correct chain-rule
   derivation and cross-checked against an independent Python
   computation before being used anywhere.

3. **Windows CI generator mismatch (commit `4c6eaf6`).** The CI workflow
   hardcoded `-G "Visual Studio 17 2022"` for the CMake configure step.
   This was wrong the moment the `windows-latest` GitHub-hosted runner's
   actual installed Visual Studio moved to version 18 — the build failed
   with `could not find any instance of Visual Studio`. **Caught by the
   actual CI run failing** (run
   [41338201277](https://github.com/jagaspeakstou-netizen/nexus-workbench/actions/runs/41338201277)),
   not predicted in advance by either Claude or the candidate — this is
   exactly the kind of environment-drift bug that only shows up by
   actually building on the target platform. Fixed by removing the
   hardcoded generator and letting CMake auto-detect.

4. **`DeviceDescriptor::interface` / MSVC COM macro clash (commit
   `dec8171` → fixed in `11138f1`).** A struct field named `interface`
   compiled fine under GCC/Clang on Linux (where this project was
   developed) but broke MSVC, which `#define`s `interface` to `struct`
   via `<combaseapi.h>` for COM programming. **Caught by the actual
   Windows CI run failing**, with a cascade of confusing C2236-class
   syntax errors starting at the field declaration. Fixed by renaming
   the C++ identifier to `connection_interface` (keeping the JSON wire
   field as `"interface"` for frontend compatibility).

5. **`-Wshadow` bug in `hardware_mocks.cpp` (Day 11 validation pass).**
   A loop variable `t` in `read_telemetry()`'s device-lookup loop shadowed
   the outer `double t` (the simulated session clock) — compiled and ran
   correctly, but was a genuine readability/maintenance hazard. **Caught
   by actually running a `-Wshadow` build**, not spotted by inspection —
   the whole point of running that check. Fixed by renaming the loop
   variable.

6. **`run_batch_parallel(num_workers<=0)` silent zero-result bug (Day 11
   validation pass).** Calling this function directly with
   `num_workers = 0` spawned zero worker threads, so the pre-sized result
   vector was returned completely unpopulated (default/zero `CaseResult`
   entries) instead of raising an error — a latent footgun not reachable
   through the benchmark CLI/API (which always clamps worker counts to
   `>= 1`) but a real gap in the function's own contract. **Caught by
   Claude reading the implementation directly** during the Day 11
   edge-case audit (not from a failing test — there was no test covering
   this input at all until one was added alongside the fix). Fixed with
   an explicit `std::invalid_argument` guard and a new regression test.

## Item 7: a deliberate AI challenge test (candidate-directed)

Reviewing this project's actual development history turned up no
genuine instance of the candidate personally catching a technical AI
error during organic development — the candidate's engagement in the
project's chat history was direction and confirmation ("do it
perfectly", "proceed", "yes"), not line-by-line technical review, which
is an honest fact about how this collaboration ran. Rather than invent
a false memory of such an instance, the candidate directed a different,
explicitly-labeled exercise: a controlled, adversarial test in which the
AI was posed a real forward-looking engineering question about the
Thermal module, produced a plausible-but-incorrect answer, and the
candidate had that answer independently verified — against the
governing equation, the closed-form analytical solution, and the real
GoogleTest suite — before any judgment was made about whether to accept
it.

**This is not a reconstruction of an earlier catch and is not presented
as one.** It is recorded here as exactly what it is: a deliberate test
designed by the candidate and carried out on an isolated git branch
(`review/ai-challenge-thermal-fea`), never touching the committed
implementation on `main`.

**The question posed:** how to generalize the element load-vector
formulation for per-element, piecewise-constant heat generation.

**The AI's answer (verbatim):** proposed assigning the *full*
`q_e·A·h` to each of an element's two nodes, rationalizing that halving
is "already absorbed" by the assembled matrix summing contributions at
shared interior nodes.

**Verification outcome:** incorrect, confirmed three independent ways —
(1) re-derivation from the governing weak-form integral (the correct
split is `qAh/2`, matching the project's own existing derivation doc and
the committed code), (2) an independent from-scratch Python
re-implementation showing the proposed formulation injects exactly 2×
the physically correct total heat and produces a 125 °C temperature
error at the domain midpoint — with a closed-form algebraic prediction
of that exact error matching the measured result, and (3) temporarily
building the incorrect formulation into the real `thermal.cpp`, which
made 3 of the module's 10 tests fail with that same ~125 °C
discrepancy (one of them — the mesh-convergence test — failing in a
second, independently diagnostic way: the error no longer *shrinks*
under mesh refinement, the signature of an energy-balance bug rather
than a discretization-accuracy one).

No change was made to the committed implementation — `thermal.cpp`
already used the correct formulation, and `git diff` against `main`
after reverting the test patch shows zero difference.

Full record (exact prompt, exact AI response, full derivation, all three
verification methods with their raw output, and reproduction
instructions):
[`docs/technical_report/ai_challenge/THERMAL_LOAD_VECTOR_CHALLENGE.md`](ai_challenge/THERMAL_LOAD_VECTOR_CHALLENGE.md).

## Item 8: a real, organically-caught packaging defect (2026-11-02)

Unlike Item 7 above (a deliberate test, explicitly because no genuine
catch had occurred by that point), this one is a genuine, unplanned
catch during final submission packaging — the kind of entry the brief
originally asked for.

**What happened:** `docs/packaging/windows.md` and `REPORT.md` both
claimed, based on a CI run's process-liveness check, that `Launch.exe`
had been "confirmed" launching successfully on a real Windows runner.
That claim was never actually checked against the run's own screenshot
artifact — the candidate downloaded and personally opened it for the
first time during final verification, which revealed `Launch.exe` had
actually hit its own `ShowWebView2MissingError()` dialog, not a working
window. The underlying verification logic
(`.github/workflows/windows-build.yml`'s original launch-check step,
and the claims built on top of it in the docs) was wrong: it checked
only `-not $proc.HasExited`, which is true even while a modal error
dialog is showing.

**How it was caught:** not by a test, not by a deliberate challenge —
by the candidate actually opening evidence that already existed but had
never been looked at, exactly the gap §8 of `docs/packaging/windows.md`
and §6.1/§8 of `REPORT.md` had themselves flagged as a disclosed
limitation ("the screenshot's visual contents were never inspected").

**First root-cause theory (2026-11-02, round 1) — tested and found
wrong:** `windows-latest` GitHub Actions runners are Windows Server
images, not Windows 11 client — visible directly in the screenshot's
own desktop watermark ("Windows Server 2025 Datacenter"). The
hypothesis was that Server doesn't ship the WebView2 Runtime
pre-installed the way Windows 11 client does. A fix was pushed
(install the Runtime in CI, and detect the error dialog via an exact
`FindWindow` title match instead of trusting "process alive" alone)
and a fresh CI run went green — but the candidate pulled the new
screenshot and **the same startup-error dialog was still showing**,
disproving the theory outright: the run's own log showed the WebView2
Runtime was already present (v155.0.4283.62), confirmed by the
registry check added for exactly this purpose. Worse, the hardened
detection itself had a second bug — the exact-title `FindWindow` match
silently failed (the dialog's title was independently garbled by an
MSVC source-encoding issue, below), so the CI job reported "success"
a second time despite the launch still failing. Caught again only by
the candidate personally inspecting the new screenshot.

**Second round (2026-11-02):** rather than guess a third root cause,
two real fixes were made instead of one more theory:
1. **Diagnostics, not guesswork** — `Launcher.cpp` now logs the actual
   `HRESULT` and system error text from the failing WebView2 call to
   `launcher_error.log` beside `Launch.exe` (`LogStartupFailure()`),
   and CI copies/inlines that file into the run's evidence. The next
   run will show the *real* error code instead of another guess.
2. **The detection bug itself, fixed properly** — the exact-title
   `FindWindow` match is replaced with `EnumWindows` + a substring
   check for `"Startup Error"` across every top-level window title,
   which cannot be defeated by an exact-string/encoding mismatch the
   way the previous check was. Separately, the garbled title itself
   (an em-dash literal in the `.cpp` source being mis-decoded by MSVC)
   is fixed by switching to a `—` escape sequence plus an explicit
   `/utf-8` compiler flag in `CMakeLists.txt`, so the title renders
   correctly regardless of source-encoding assumptions.

**Round 3 (2026-11-02) — the actual root cause, from the first real
diagnostic run:** `launcher_error.log`'s first real run showed:

```
[CreateCoreWebView2EnvironmentWithOptions] HRESULT=0x800401f0 (CoInitialize has not been called.)
```

`CO_E_NOTINITIALIZED` — `Launcher.cpp` never called `CoInitializeEx`
before using WebView2's COM-based environment-creation API. This was
the real cause all along; neither the WebView2 Runtime's
presence/absence (round 1) nor the detection bug (round 2) was it —
both of those were real, separate bugs, just not the one causing the
dialog. Fixed with one call: `CoInitializeEx(nullptr,
COINIT_APARTMENTTHREADED)` near the top of `wWinMain`, paired with
`CoUninitialize()` on every exit path, plus linking `Ole32`
(`windows/launcher/CMakeLists.txt`).

This three-round sequence — wrong theory, a second bug hiding the
first fix's own failure, then a real fix once real diagnostics existed
— is left in this log exactly as it happened, not cleaned up into a
single confident paragraph.

Full detail: [`docs/packaging/windows.md`](../packaging/windows.md).

**Round 4 (2026-11-02) — "VERIFIED" was premature again.** Run
41383120271 passed every check (no error dialog, real window title, 63/63
tests) and I wrote "VERIFIED" from its text log. The candidate then
opened that run's screenshot: the window was **blank white**. The checks
could only see titles and processes, not content. Cause: the Vite bundle
uses absolute `/assets/...` URLs and module scripts, which cannot load
from the `file://` URL the launcher navigated to. Fix: the backend now
serves the built frontend over HTTP and the launcher navigates to
`http://127.0.0.1:8787/`; CI now asserts the SPA is served and that the
window's pixels are not near-white. This is the third wrong "it works"
conclusion in this item; each was caught by looking at the actual
screenshot, which is why no further claim is made here until a fresh
run's screenshot has been looked at.

**Status:** round 4 fix pushed; re-verification pending.

## What this log does not claim

- It does not claim every line of generated code was perfect on the
  first attempt beyond what's listed above — only that nothing broken
  was knowingly left in a commit without disclosure.
- It does not claim the candidate reviewed every individual line of
  generated C++ in real time; review was concentrated at module
  boundaries (does the test suite pass, does the architecture doc's
  claimed result match the actual CSV/CI output, does the disclosed
  limitation read honestly) rather than line-by-line diffing of
  AI-written code.
